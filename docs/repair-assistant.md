# 选做实战：从失败测试到修复交付

这个案例把前面的模型调用、工具执行、权限边界和验收接到一起：让 Agent 阅读一个有缺陷的 Java 日期解析器，修改解析表达式，运行测试，最后交付差异与结果。

它是一个受限练习。模型只能在四个明确允许的日期解析表达式之间修改，不能自由生成任意 Java 类，也没有 Shell。测试文件只读。我们验证的是“根据失败证据提交受限补丁，再用真实测试验收”，不是对任意用户仓库的自动修复能力。

## 先跑一次

需要 JDK 17、macOS 或 Linux。Windows 的目录权限与进程行为未验证，本例依赖 POSIX 私有目录权限。

在 `examples/agentscope-ddd` 中：

```bash
# 已按主 README 配好环境变量 DEEPSEEK_API_KEY
./run-repair.sh deepseek

# 本地 Ollama 需先启动服务并准备模型
OLLAMA_MODEL=qwen2.5:0.5b ./run-repair.sh ollama
```

模型名称、超时、迭代上限和密钥规则沿用 `config/application.properties`。研发任务与系统提示词分别放在 `config/repair-task.txt`、`config/repair-prompt.txt`；通用助手仍使用原来的提示词和 `./run.sh` 入口。

每次启动创建新的私有临时练习目录。模型不能指定项目路径；运行结束后删除临时源码与编译产物，终端保留差异与验收记录。想保存过程，可以把终端输出写入自己的日志文件，分享前检查内容。

## 这次到底修什么

原来的解析表达式是：

```java
LocalDate.parse(date, DateTimeFormatter.ofPattern("yyyy-MM-dd"))
```

默认 SMART 解析会把一些非法日期调整到月末，导致 `2025-02-29`、`1900-02-29`、`2025-04-31` 被接受。本例用七个固定输入检查返回值，既覆盖非法日期，也保留闰年、普通日期和年份下界。

仅把 `yyyy` 改成 `uuuu`，仍然是 SMART，三个失败不会消失。允许的正确修改包括 `DateTimeFormatter.ISO_LOCAL_DATE`，或 `uuuu-MM-dd` 配合 `ResolverStyle.STRICT`。这不是枚举模式名字就算修复：每次验收都会真实启动 `javac` 和 `java`。

## 一轮修复由谁推进

1. 程序创建固定练习，先运行基线测试，确认确实存在失败。
2. Agent 收到任务和基线输出，调用 `read_project_file` 读取源码、测试。
3. Agent 选择完整的新表达式，通过 `replace_expression` 提交修改。
4. 工具核对文件名、旧表达式、白名单与完整源码模板，然后原子写入并回读。
5. Agent 调用 `run_project_tests`，取得真实结果。允许的错误补丁仍可能失败，需要继续调查。
6. Agent 正常返回后，程序再次编译和执行测试。只有正常模型结束、最终测试通过且有真实差异，任务才输出 `PASS`。

模型说“全部通过”，不能跳过第六步。达到循环上限、模型异常、没有修改或最终测试失败，都会使任务无法判为完成。

## 分层和代码位置

| 位置 | 职责 |
| --- | --- |
| `bootstrap/RepairMain` | 装配独立入口、配置、项目与 Agent，关闭资源，返回进程退出码 |
| `app/RepairService` | 基线、模型执行、程序复验与最终判定 |
| `domain/RepairProject` | 受限项目端口，包含读取、替换、测试、差异 |
| `infra/repair/RepairTools` | 将项目操作暴露为三个 AgentScope 工具，记录调用及拒绝 |
| `infra/repair/RepairWorkspace` | 私有目录、模板核验、原子修改、固定编译测试及清理 |
| `infra/AgentScopeGateway` | 复用原有模型接入，注入本次工具集和系统提示词 |
| `src/main/resources/repair` | 可信源码模板与只读测试资源 |

测试模板不靠模型维护，原始事实和验收条件也不交给模型改写。`RepairProject` 让应用组织过程，基础设施负责文件和进程细节；没有另造一套 Agent Loop。

## 哪些边界已经落实

- 工具只接受两个固定文件名；绝对路径、点路径、符号链接和修改测试都会被拒绝。
- 替换前校验整个源码模板，不只搜索某一行；额外 import、静态块和未知表达式都不能进入编译。
- 每次测试从校验过的字符串创建全新私有快照，不加载旧 class、不运行工作区构建脚本。JDK 路径与命令参数由程序固定，不经过 Shell。
- 子进程不继承 API 密钥或 JVM 注入环境变量；限制堆、元空间、输出大小和等待时间。这里没有承诺限制全部原生内存，也没有提供操作系统沙箱。
- 模型工具最多调用 16 次，其中测试最多 6 次；再给程序基线和最终复验各留一次。每个编译或运行进程限时 20 秒，终止和收尾另有等待。

这些边界针对自带练习和模型输入。它不是同一操作系统账号下恶意进程之间的强隔离，也不能拿来直接执行任意下载的源码。若以后开放用户仓库，必须重新设计沙箱、资源访问、构建依赖和确认流程。

## 验证成功，也验证没有成功

从仓库根目录执行：

```bash
./mvnw -f examples/agentscope-ddd/pom.xml test
```

离线测试使用真实编译运行验证四种表达式状态，并检查以下反例：

| 场景 | 验收 |
| --- | --- |
| 原始 SMART → 严格解析 | 基线失败，修复后七个日期检查通过 |
| 只将 yyyy 改为 uuuu | 仍失败，不能当作有效修复 |
| 模型只回答“修好了” | 原始工具事实未变，最终复验失败，输出 NOT_COMPLETED |
| 越界、符号链接、改测试或注入任意表达式 | 拒绝，原文件或外部哨兵文件保持不变 |
| 源码模板之外出现改动 | 在编译之前拒绝 |

2026 年 10 月 24 日，当前实现的独立测试结果为：DDD 示例 18 项通过，根工程 86 项通过。两组测试分别验证示例与原工程回归，不代表 104 次真实模型修复。

同一天使用现有模型配置运行，结果如下：

| 模型 | 实际过程 | 程序验收 |
| --- | --- | --- |
| DeepSeek deepseek-flash | 读取两份文件、替换表达式、运行测试，再返回说明 | 最终七项检查通过，有真实差异，退出码 0 |
| Ollama qwen2.5:0.5b | 返回说明，未调用修复工具 | 原始三个失败仍在，无差异，退出码 2 |

DeepSeek 这次的日志摘录如下，省略了模型说明与重复的工具返回行：

```text
[基线] FAIL
[研发工具 #2] read_project_file
[研发工具 #1] read_project_file
[研发工具 #3] replace_expression
[研发工具 #4] run_project_tests
[模型结束] MODEL_STOP
[最终复验] PASS
[任务] PASS
```

两个读取可以并行，因此日志编号的出现顺序不必递增。编号用于关联工具事件，不是对整个执行流程重新排序。

本地小模型的负例同样重要：接通模型不代表它会完成工具任务。此次结果仅适用于这次运行与这个模型配置；换用其他 Ollama 模型后，应重新观察工具调用和最终复验。

模型说明统一放在 `[模型说明，非验收]` 后，换行和控制字符被转义成可见文本。模型无法通过输出另一行 `[任务] PASS` 冒充程序验收，但转义本身不会检查说明内容是否正确。

## 可以怎样继续扩展

先增加日期边界测试，观察允许的修改是否仍能满足新要求。若要增加别的修复任务，可以增加独立可信模板与明确变更契约。不要因为这次能修一个表达式，就把工具升级成任意写文件和任意执行命令。

本例完成了单 Agent 的调查、修改、测试和最终交付。多 Agent 分工、通用代码补丁和用户项目接入都没有实现，也不是这个选做案例的验收条件。
